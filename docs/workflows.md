# The four workflows

Where each part of Syllabus Model Lab runs, how it is started, how far it has
been verified, and what is known to be missing. The detailed documents are
linked from each section; this page is the map.

Status words:

- **Verified in production**: exercised on `aiswe.uwb.edu` (and Tillicum where
  relevant) with the result recorded in
  [verification-history.md](verification-history.md).
- **Verified by tests**: covered by the repository's suites, including the tests
  that run the real operator scripts against fake `systemctl`, `ssh` and
  `curl`, but not exercised live since the last change that could affect it.
- **Experimental**: works when driven by hand and has produced artifacts, but is
  not part of the production path, and nothing in the application depends on it.

## 1. VM inference

**What it is.** Base and RAG are answered by the VM's main Ollama on
`127.0.0.1:11434` (`llama3.2:3b`; retrieval embeds with `nomic-embed-text`).
Fine-Tuned and Fine-Tuned + RAG are answered by the `aiswe-finetuned` user unit
on `127.0.0.1:9001`, which asks a second Ollama on `127.0.0.1:11435` for the
course's own model (`FROM llama3.2:3b` plus the adapter), so the base model and
the course model never evict each other. One bounded queue in the backend runs
every generation one at a time (`GENERATION_MAX_CONCURRENCY=1`, 160 waiting,
150 s queue timeout, under Nginx's 300 s read timeout). A course answers with
the version that is **activated** (`deployment = online`), and activation
refuses a version the service does not list. See
[architecture.md](architecture.md#request-flows),
[classroom-capacity.md](classroom-capacity.md),
[deployment.md](deployment.md#fine-tuned-inference-on-the-vm).

**Entry points.** Nothing to start: three units with lingering (`aiswe-backend`,
`aiswe-finetuned`, the system units `ollama` and `ollama-finetuned`). Checks:

```bash
./scripts/aiswe_finetuned.sh check
```
```bash
./scripts/classroom_gpu_mode.sh status
```
```bash
AISWE_VERIFY_PASSWORD='<admin password>' backend/.venv/bin/python scripts/verify_finetuned_production.py --admin-email <admin email> --course css360d-fall-2026-q0ne --course css360e-autumn-2026-c08m
```

**Verified.** The production configuration (one uvicorn worker, the Nginx
`/api/` block, both Ollama units, the mapping, the watchdog) was read and
recorded on 2026-10-31, and the deployment of `568a480` the same day passed the
verify script for both Fall courses with all four conditions answering from
each course's own model
([verification-history.md](verification-history.md#deployment-of-568a480-2026-10-31)).

**Known gaps.** About three simultaneous four-condition comparisons is the CPU's
limit; beyond that students are told "busy" rather than failed
([classroom-capacity.md](classroom-capacity.md)). HTTP/2 is not enabled on
the TLS listener. A stopped `aiswe-finetuned` is restarted only by the fallback
scripts' restore or by hand. A starter seed job holds the single generation
slot, so keep `AUTO_STARTER_SEED_GENERATION=false` and do not upload a syllabus
during class.

## 2a. Classroom GPU mode

**What it is.** For one class, all four conditions are generated by the Tillicum
GPU service through a tunnel on `127.0.0.1:9101`; the backend reads a mode file
before every generation; a watchdog timer fails back to the VM on expiry or
three failed health checks. `aiswe-finetuned` stays up as the failback target.
See [classroom-gpu-mode.md](classroom-gpu-mode.md) and the
[runbook](classroom-gpu-runbook.md).

**Entry points.** `./scripts/classroom_gpu_mode.sh start|status|stop` (signs in
as an administrator; needs a Tillicum serving job started with
`./training/start_finetuned_service.sh` after a Duo prompt).

**Verified.** Used in class on 2026-10-01/02. On 2026-10-31 the mode file read
`vm`, the timer was enabled and firing every 15 s, and both watchdog units were
identical to the tracked templates. Switching itself needs an allocation and
was not exercised on 2026-10-31.

**Known gaps.** A Tillicum session lasts one hour under the `debug` QOS. The
watchdog judges `/health` only, not generation (audit finding B16).

## 2b. Emergency fine-tuned fallback

**What it is.** When the VM cannot serve the fine-tuned conditions (its Ollama
is broken, an adapter is not converted yet), a tunnel forwards `127.0.0.1:9001`
to a Tillicum GPU service. The VM unit must be stopped first because both own
the same port; the scripts record that stop and restore the unit when the
fallback ends or fails. See
[tillicum-operations.md](tillicum-operations.md#inference-the-tillicum-fallback)
and [deployment.md](deployment.md#tillicum-fallback-and-back-again).

**Entry points.**

```bash
./scripts/start_finetuned_tunnel.sh --from-backend --stop-local
```
```bash
./scripts/status_finetuned_tunnel.sh
```
```bash
./scripts/stop_finetuned_tunnel.sh
```

**Verified.** By `training/test_finetuned_fallback_scripts.py`, which runs the
real scripts against fakes, including a backend that answers
`/api/fine-tuned/health` with 401 as production does. From 2026-09-04 (when
that route became administrator-only) to 2026-10-31 the start script probed it
bare, died at its last step and rolled a working fallback back; the status
script called a healthy service unavailable. Both were repaired in `ef7b7c7`.
The fallback has **not** been rehearsed live since.

**Known gaps.** A publication accepted while the tunnel is the serving path is
only proven servable on Tillicum; after `stop_finetuned_tunnel.sh` restores the
VM unit, run the verify script for the activated courses. Rehearse the
fallback deliberately, outside class, before relying on it.

## 3. Tillicum training

**What it is.** A professor's model request becomes a queued run; the worker on
Tillicum (started by a person after a Duo prompt) flushes pending reports,
reconciles lost submissions, claims the run, syncs the dataset from the VM,
launches the QLoRA job, and records the Slurm job id. The job reports its own
completion from the compute node; the backend registers the version
`ready`/`offline`. Serving it is a separate decision: install and map on the
VM, then activate from Admin → Models. `promote_qlora_adapter.sh` is the legacy
publication path and is now held to the same servability check. See
[tillicum-operations.md](tillicum-operations.md),
[training/README.md](../training/README.md),
[architecture.md](architecture.md#the-training-lifecycle).

**Entry points.** On Tillicum, from the cluster checkout:

```bash
./training/run_training_queue.sh --once
```
```bash
./training/run_training_queue.sh --once --dry-run
```

**Verified.** The lifecycle has run in production: dataset transfer, training,
completion callback from the compute node, automatic registration, "registered
is not published" (entries of 2026-08 and 2026-09 in
[verification-history.md](verification-history.md)). The 2026-10-31 changes
(a finished run stays finished; a refused publication is final) are covered by
the backend route tests and the worker tests, including an end-to-end
fake-backend run; after the deployment of `568a480` the worker tests and a dry
run passed on Tillicum.

**Known gaps.** The dataset a run trains on is not pinned to the run (B10); the
launcher's existing-job short-circuit can attribute another run's job (B12); a
job that dies without its trap strands the run at `submitted` (B15); a
completion refused with a status other than 404/409 is retried on every flush
(L1). Training-time prompt rendering differs from serving-time rendering
(B14). All are listed in [remaining-work.md](remaining-work.md#8-open-findings-from-the-2026-10-27-audit).

## 4. VM CPU training (experimental)

**What it is.** The same trainer on the VM's CPU: `train_qlora.py --cpu`
through `./training/start_cpu_qlora_training.sh --smoke` and then `--full`,
registration by hand with `scripts/register_course_model.py`, conversion and
mapping with `scripts/install_finetuned_adapter.py` and
`scripts/aiswe_finetuned.sh set-mapping`, then activation. See
[training/README.md](../training/README.md#cpu-training-on-the-uwb-vm-no-tillicum)
and the lineage notes in [css360-model-evolution.md](css360-model-evolution.md).

**Verified.** Only by tests of the CPU mode and launcher
(`training/test_train_qlora_cpu_mode.py`, `training/test_qlora_training_helpers.py`)
and by one hand-run artifact: `css360-cpu-v3-test:latest`, mapped on the VM as
CSS 360 `v3`. No complete cycle from a CPU run through registration to an
activated version serving a class has been recorded. The VM also holds an
untracked local script, `training/train_cpu_qlora_experiment.py`, from the
2026-09-08 experiment; it is not in the repository, and a `git pull` never
touches it.

**Known gaps.** The queue worker targets Tillicum only; nothing drives a CPU run
automatically; about an hour per full run for a 48-example course, sharing the
8 vCPUs with the backend and both Ollama servers, so never during class. Making
VM training independently usable is the stated long-term goal
([remaining-work.md](remaining-work.md#6-fine-tuned-inference-without-tillicum)).

## What must stay true across all four

- **One owner of `127.0.0.1:9001`**: the VM unit or the emergency tunnel, never
  both. The scripts enforce it; do not start either by hand.
- **Serving follows activation.** Registering, training, publishing from
  Tillicum or mapping on the VM never changes which version answers; only
  activation (or a publication that passes the same check) does, and both
  refuse a version the fine-tuned service cannot serve.
- **The mode file decides GPU mode.** `~/.config/aiswe/generation-mode.json`
  is read before every generation; `classroom_gpu_mode.sh` and the watchdog are
  its only writers.
- **A fast-forward pull changes tracked files only.** Untracked local files,
  ignored env files and every model artifact survive it; never run
  `git clean`, `git stash -u` or `git checkout .` on the VM or Tillicum.
